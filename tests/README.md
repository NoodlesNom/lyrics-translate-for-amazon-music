# Tests

End-to-end tests that load the unpacked extension (`../extension`) in headless Chromium with Playwright and run it against `mock.html`, a local copy of the structure of Amazon Music's full view (the expanded Now Playing overlay: art, title, artist, transport, and the lyrics column `Stage_OverlaysContainer`, filled for songs with lyrics and empty/0 px wide for songs without, with the geometry measured on the live site at 1600x820) and of the mini-player's markup (test IDs, ARIA labels, the "Lyrics available" badge, the Enter Full Screen button). The full view can be opened/closed, and the mini-player title can be absent, hidden or visible while it's open. `music.amazon.com` is routed to the mock page, Google Translate requests are answered from `fixtures.json`, and the Gemini API is mocked with a placeholder key (no real key is used or needed).

All lyric lines in `mock.html`, `fixtures.json` and the tests (including the mocked LRCLIB answers) are invented test text.

```sh
cd tests
npm install
npx playwright install chromium
npm test
```

- `test.js`: rendering, layout, romanization/translation, settings, floating button, selectors, failure handling.
- `test-gemini.js`: Gemini translator, fallback to Google, skipping songs already in the target language (incl. look-alike letters, symbols, mostly-English songs and stale caches), status dot, popup "This song" line and button, LRU cache and counter.
- `test-lrclib.js`: the LRCLIB fallback for songs Amazon has no lyrics for (lrclib.net is mocked): no-lyrics detection from the mini-player badge and the full view's empty lyrics column (badge present, absent, late, other badges, no song; mini-player title absent while the full view is open), song identity from `Stage_Title`/`Stage_Subtitle`, the clock from the slider's aria-label (m:ss and h:mm:ss, with or without aria-valuenow/max, generic slider fallback), placement in Amazon's lyrics spot (clear of art, title and controls; on resize), Amazon-like styling, no panel on the normal page, synced highlighting and scrolling with seek/pause, removal on full view close / song change / Amazon lines appearing, matching, translation and text size of the fetched lines, cache and 7-day "not found" marker, rate limiting, the popup toggle and the "This song" notices (full view open and closed). It also covers the v1.3.3 language skip for LRCLIB lines (English lyrics with symbols and a look-alike letter, a mostly English song with two Japanese lines, a stale Gemini cache) and writes `fullview-1.3.2.png`.
- `test-update.js`: the v1.3.4 update notice (api.github.com is mocked). The real unpacked folder (`chrome.management.getSelf()` says `development`, without the `management` permission): check ~5 s after start, stored result, NEW badge, popup update line/link/how-to, "Check for updates" with "Checking…", up to date / newer / older / 403 / 429 / offline / 404, the 60 s cooldown ("Checked just now"), the daily and 3 h retry timing triggered by the popup and content-script messages, numeric version compare and install-type rules. Store copies (a temporary copy whose `getSelf()` is stubbed to `normal` or `sideload`) make zero GitHub requests and show no badge or update UI. The other suites answer GitHub with the installed version.
- `test-scroll.js`: the v1.3.5 fix for Amazon's full-view lyrics scrolling. `mock.html?amz=scroll` (with a 40-line song) reproduces Amazon's scrolling as measured live: after a seek no line is white for a moment, then Amazon jumps to line index × 53 px (its own row height, ignoring the extension's taller rows) and repeats that 400 ms later; ordinary line changes are smoothly centered; wheel input pauses Amazon's auto-scroll for 3 s. Checks: the bug is reproduced (Amazon alone leaves the line far below the visible area), after seeks at 145% and 100% text size the white line is fully visible and centered within 500 ms and stays so after Amazon's second jump, bounded extension scrolls per seek and zero scroll events while nothing changes, no extra scrolling during steady playback, a user wheel pauses auto-centering for 3 s, size/translation/original/romanization toggles, nothing done while no line is white, and the LRCLIB lyrics (their own scroller) behave as before.
- `test-popup-fit.js`: the v1.3.5 popup fit (since 1.3.6 the longest LRCLIB note is the "already romanized" one, and all five checkboxes, including "Find lyrics when Amazon has none", must sit left of their text with the same size, gap, font and alignment). Browsers size an extension popup to its content, capped at 800x600 px; the test loads `popup.html` as a real extension page, measures its preferred size, sets the viewport to that size (capped like a real popup) with classic, space-taking scroll bars and checks that the document has no vertical or horizontal overflow and stays at most 590 px tall. States: an unpacked copy with an update available (update line with how-to, version, "Check for updates") and a store copy (no Updates UI rendered at all), each as opened and with the longest status lines (long title and artists, language/translation state, LRCLIB notice, button message, counter, update-check error) at all four text sizes, plus an unbreakable title/URL. Any element that can scroll must use a thin, themed scroll bar and horizontal scrolling is off. The in-page panel on the mock page is checked too: it grows to fit the popup (no scroll bars in a tall window) and in short windows only the popup's inner area scrolls. Writes `popup-fit-after-*.png`.
- `test-romanized.js`: the v1.3.6 handling of romanized LRCLIB lyrics (Japanese romaji, Korean romanization, pinyin; all invented). Detection in the service worker (romaji with and without macrons and with an English line, Korean, pinyin with and without tone marks → flagged; four invented English songs with vowel-ending words, "go go go", "na na na" and Japanese loanwords, plus Spanish, Italian and Indonesian songs, a Japanese-script song, a 2-line song and an English song with two romaji lines → not flagged) and the local hiragana guess. A Japanese-script copy in the LRCLIB search results (same artist, duration within 3 s) is preferred over the romaji one (one extra `/api/search`, no new data). Without one: Google is mocked like the real one (romaji, Korean romanization and pinyin come back unchanged, only kana sent with sl=ja is translated), so romanized Japanese lines are sent as their hiragana guess with sl=ja and get a real translation as the main line, the romaji in the romanization slot under it; when Google translates nothing, the romaji is the main line, shown once, and the popup says "Romanized lyrics, no translation available" (pinyin: sl=zh-CN, echoed, not used); a mostly-romaji song with pure English and mixed (romaji + English phrase) lines while Google reports English for everything: the mixed lines count as romanized and get a translation from their hiragana guess (English phrase kept in Latin letters), only the pure English lines are left alone, and the popup never says "Already in English"; the text itself is never repeated as the original, "Original lyrics" shows a marked hiragana guess (Japanese, no Gemini), Gemini's Hangul guess (Korean with Gemini) or nothing (pinyin without Gemini), Romanization/Translation toggles and text size, the English line stays ordinary. Gemini's object reply (`lang` + per-line translation and original-script guess) and its verdict overriding the heuristic (Korean instead of Japanese; "none" → ordinary lines). Popup status lines ("LRCLIB lyrics were already romanized (…)"). Cache: v2 LRCLIB entries, 1.3.5 entries holding romaji looked up again (old translations dropped), non-romanized 1.3.5 entries kept, pre-1.3.6 song entries of romanized songs and entries from the first 1.3.6 build (rv 2, echoed romaji stored as no translation) and from the second (rv 3, mixed lines stored as English) reset (rv 4). Writes `popup-romanized.png`, `fullview-romanized*.png`.
- `test-gemini-dot.js`: the v1.3.6 Gemini status dot on the floating button (Gemini mocked, placeholder key): none with Google (by default without a key, or chosen), gray without a key / not used yet, green after a reply, amber for quota and timeout, red for a rejected key, same state and color as the popup's indicator, live updates (no reload) including switching translators (also without a key: Gemini → gray, Google → none), tooltip text, ~8 px in the bottom-right corner with a dark ring and never dimmed, the key never in the page, gone with the floating button. Writes `float-dot.png`.
- `test-extra.js`: recovery after a failed request (takes about a minute).
